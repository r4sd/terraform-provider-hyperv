# ADR-0003: 品質ゲート

## 現在の決定

**マージのゲートは「CI green」ではなく「CI green かつ批判的レビュー完了」。**
レビューは PR 作成と**同時に**起動して CI と並走させる。直列にしない。

現行のルール本体は `CLAUDE.md`(シャドウ移行 DoD)にある。ここには**なぜそうなったか**を残す。

## 2026-07-19: 移行の「完了」を定義する

### 背景

シャドウ移行([ADR-0002](0002-shadow-migration.md))を 1 機能ずつ進める中で、
**どこまでやったら「その機能は移行できた」と言えるのか**が曖昧だった。

曖昧なままだと「動いたから完了」になり、次のような状態で先へ進んでしまう。

- 実機で一度も試していない
- 単体テストは通るが、実際には PS へ落ちている
- 型の出典が公式資料ではなく、他プロジェクトのコードの写し

### 決定

**1 機能 = 1 縦スライス**とし、順序を固定したパイプラインを定めた(`CLAUDE.md` §1)。

```
① 一次資料(MOF)で名前・型・単位・列挙値を確認 → fixture 化
② CIM プリミティブを TDD で実装(golden → RED → GREEN)
③ provider 側のシャドウ実装(read 変換 / write 逆変換 + ガード)
④ 単体テスト(変換・ガード・境界)
⑤ 実機での受け入れテスト
⑥ PR 作成 → CI と批判的レビューを並走
⑦ 両方揃ってからマージ判断
```

さらに「機械が強制するもの」と「人が守るもの」を明確に分けた。

| 区分 | 内容 | 誰が守るか |
|---|---|---|
| **Hard gate** | build / vet / test / lint / CodeQL / govulncheck / gofmt / CIM 照合 | **CI が落とす**(記憶に依存しない) |
| **Soft rule** | 一次資料検証・TDD 先行・WHY コメント・実機確認・批判的レビュー | 人が守る(DoD に明文化して必須確認項目にする) |

### 根拠

**分けたのは、「規約に書いたから守られる」わけではないから。**
機械化できるものは CI に落とし、できないものだけを規約として残す。
両者を混ぜると、規約全体が「努力目標」になって形骸化する。

### 未達をどう扱うか

上位のゴール(例: フルライフサイクルの PS 0 件)に届いていない場合は、
**残る部分を正確にスコープ明記する**ことを DoD に含めた。

> どの field / VM 世代 / 条件が残 PS か。「達成した」と曖昧に丸めない。

これは [ADR-0002](0002-shadow-migration.md) の「現時点で PS に落ちる範囲」を
正直に列挙している理由でもある。

## 2026-08-01: 批判的レビューを CI と並走させる

> この節は、上のパイプライン ⑥ が**なぜ「並走」と書かれているか**の記録。

### 背景

当初、批判的レビューは**レビュー → PR 作成**の順(直列)で回していた。

レビューは実測 4〜7 分、CI は 2〜3 分かかる。直列にすると
「実機まで通ったのに、まだ PR を作れない」待ち区間ができる。

### 何が起きたか

**2026-08-01、3 つの PR で連続してレビューを飛ばした。**

理由は単純で、CI が green になった時点で「終わった」と感じてしまうため。
待ち区間が「余分な手間」に見え、省略の動機が生まれる。

事後にレビューを回したところ、**CONFIRMED の指摘が 1 件出た**。
内容は「手書きの golden file が、実機に存在しない挙動を仕様として固定していた」というもの。

これは CI では絶対に検出できない。**golden file が間違っていると、CI はむしろ緑になる。**

### 決定

**PR 作成と同時にバックグラウンドでレビューを起動する。**

こうするとレビューの待ち時間は CI の待ち時間に吸収され、実質の追加コストは 2〜4 分。
CI 待ちの間に別の作業をしていれば体感はほぼゼロになる。

そして**マージのゲートを言い換えた**。

> ゲートは「CI green」ではなく **「CI green かつレビュー完了」**。片方だけでマージしない。

### 根拠

**省略の動機そのものを消した**のが本質。
「飛ばすな」と規約に書いても、待ち時間があれば飛ばされる。
順序を変えて待ち時間を消せば、飛ばす理由がなくなる。

これは [ADR-0002](0002-shadow-migration.md) の設計判断と同じ考え方で、
**規律に頼らず構造で解決する**方を選んでいる。

### レビューの依頼のしかた

手順を細かく書かず、**何を検証してほしいか**と**判定 + 結論**を求める形にする。
「ここが怪しい」と思っている箇所は伝えてよいが、
「そこに限らず見てほしい」と添えて視野を狭めない。

手順はパイプラインの実行者側が担い、レビュー側には「何を検証するか」だけ渡す。

## 2026-07〜08: 事故から導いた設計ルール

`CLAUDE.md` §4 の表は、いずれも**実際に起きた不具合**から作られている。
ここではその対応関係だけ残す(ルール本体は `CLAUDE.md` を参照)。

| ルール | きっかけになった不具合 |
|---|---|
| 単位変換は read⇄write を厳密に逆にし、round-trip テストで固定する | 単位変換漏れによる恒常 diff |
| PS 0 件のための省略ガード(空・差分なしなら書き込まない) | 既定構成でも毎回書き込みが走っていた |
| 「0 = Dynamic」のフィールドは現行値へ正規化する | 正規化しないと既定構成で毎回差分が出る |
| CIM で表現できない変更は PS へ委譲する。**黙って成功報告しない** | 非ゼロ → 0 の変更が黙殺されるリグレッション |
| PS 0 件のテストには negative control を必須にする(恒真アサーション禁止) | 「PS が呼ばれない」ことを常に満たすテストは何も証明しない |
| シャドウは promotion と区別して検証する(定義元ファイルを実行時に確認) | メソッドの存在チェックはトートロジーだった |

**共通するのは「静かに間違う」ことへの対処**である点。
このプロジェクトで見つかった不具合の多くはクラッシュではなく、
成功を返しながら意図と違う結果になるものだった。

### 見直しの条件

- [ ] レビューで CONFIRMED が長期間出なくなった → ゲートの緩和を検討する(それまでは維持)
- [ ] Soft rule のいずれかが機械化できるようになった → Hard gate へ移す
