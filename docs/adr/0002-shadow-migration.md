# ADR-0002: 移行方式(シャドウ移行)

> テーマ単位のファイル。決定が変わったら**末尾に追記**する(過去を書き換えない)。
> 詳しい運用は [README.md](README.md) を参照。

## 現在の決定

**Go の構造体埋め込みを使い、移行済みメソッドだけを CIM 実装で「上書き(シャドウ)」する。**
未移行メソッドは promotion で PowerShell 実装がそのまま呼ばれる。
切り替えは環境変数で行い、**既定は PowerShell 経路**。

**PowerShell 実装は削除しない。** 恒久的なフォールバックとして残す。

## 2026-05: 埋め込みによるシャドウ方式を選ぶ

### 背景

PS 実装は 15 ファイル・約 3,900 行あり、リソースも `hyperv_machine_instance` /
`hyperv_network_switch` / `hyperv_vhd` / `hyperv_iso_image` / `hyperv_cloudinit_iso` /
`hyperv_vm_checkpoint` と広い。**一度に置き換えるのは不可能**なので、段階移行の方式を決める必要があった。

### 選択肢と評価

| 案 | 内容 | 判断 |
|---|---|---|
| A: 構造体埋め込みでシャドウ | 移行済みだけ上書き、残りは promotion で PS へ | ✅ 採用 |
| B: メソッドごとに if 分岐 | 各メソッド内で `if useWsman { ... } else { ... }` | ❌ 却下: 分岐が全メソッドに散る |
| C: 一括で置き換える | PS 実装を消して CIM 実装に差し替える | ❌ 却下: 動かなくなった時に戻せない |
| D: インターフェースを2実装 | 全メソッドを両方の実装で埋める | ❌ 却下: 未移行分の PS 実装を書き写すことになる |

### 決定

A を採用。CIM 側の `ClientConfig` が PS 側の `*hyperv_winrm.ClientConfig` を埋め込む。

```
CIM 側で同名メソッドを定義 → そちらが呼ばれる(シャドウ)
CIM 側に定義がない        → 埋め込み先の PS 実装が呼ばれる(promotion)
```

**移行の単位は「1 機能 = 1 縦スライス」**とする。CIM プリミティブの実装から
実機での動作確認まで通して 1 つの機能を移す(手順は `CLAUDE.md` の DoD、経緯は [ADR-0003](0003-quality-gates.md))。

### 根拠

**D を却下した理由が A を選ぶ理由でもある。**
インターフェースを 2 実装に分けると、未移行のメソッドも CIM 側に「PS を呼ぶだけの実装」として
書き写す必要がある。埋め込みなら**書かないメソッドは自動的に PS へ落ちる**ため、
移行済みかどうかがコードの有無で表現される。

**B を却下したのは、分岐が全メソッドに散らばるため。**
移行が完了しても分岐が残り、後片付けが必要になる。

### この方式の落とし穴

**「シャドウしているつもりで promotion のままだった」ことに気付けない。**
CIM 側の実装を書き忘れても、コンパイルは通り、テストも通り、PS 実装が黙って動く。

対策として、テストは**メソッドの定義元ファイルを実行時に確認する**。

> `runtime.FuncForPC().FileLine()` で定義元ファイルを確認する
> (`CLAUDE.md` の設計ルール表より。`assertShadowedIn` として実装)

これは「メソッドが存在するか」を調べるだけでは不十分だったため導入した。
promotion されたメソッドも存在はするので、存在チェックはトートロジーになる。

## 2026-07: 既定を PowerShell 経路のままにする

### 決定

切り替えは 2 つの環境変数で行い、**どちらも既定は無効**。

| 環境変数 | 有効時の挙動 | 既定 |
|---|---|---|
| `HYPERV_USE_WSMAN` | CIM 経路に切り替える(未移行は PS へ落ちる) | 無効(= PS 経路) |
| `HYPERV_WSMAN_STRICT` | PS フォールバックを fail-fast スタブに差し替える | 無効 |

`HYPERV_WSMAN_STRICT` は `HYPERV_USE_WSMAN` が有効なときだけ意味を持つ。

### 根拠

**既定を CIM 経路にしないのは、移行が完了していないため。**
CIM 経路には現時点で明確な穴があり(下記「現時点で PS に落ちる範囲」)、
既定にすると気付かないうちに未検証の経路を踏むことになる。

**strict モードは「PS を使っていない」ことの陽性証明として設けた。**
「PS 呼び出しが 0 件だったこと」は、普通に動かしても確認できない。
`StrictNoPSClient` は PS 実行インターフェースの全メソッドを
「呼ばれたら即エラー + カウンタ加算 + ラベル記録」で実装してあり、
1 件でも PS が走れば失敗する。

> fire-and-forget で error が握り潰される経路の検知漏れを防ぐ二重化
> (`api/hyperv-wsman/strict.go` のコメントより)

fire-and-forget な PS 実行はエラーを返さないため、戻り値だけ見ていると検知漏れする。
そのためカウンタと戻り値の両方で検出する。

## 2026-07: PowerShell 実装を削除せず恒久的に残す

### 背景

シャドウが進むと「PS 実装はいつ消すのか」が問題になる。

### 決定

**消さない。** CIM 経路で表現できない操作は、意図的に PS へ委譲する。

### 根拠

CIM で表現できない、あるいは表現すると壊れる操作が実際に存在する。

- **非ゼロ → 0/false の変更**が CIM の埋め込みインスタンス経由では送られず、**黙殺される**。
  「成功したが変わっていない」状態になるため、検出して PS へ委譲するか明示的にエラーにする
- 一部の設定(チェックポイント種別の変更など)は CIM 側の経路が確立していない

`CLAUDE.md` の設計ルールとして次を定めた。

> go-wsman で表現できない変更は PS 委譲。
> **黙って成功報告する実装は禁止**(検出 → PS フォールバック or 明示エラー)

**「PS を消すこと」は目的ではない。** 目的は
「PowerShell が無くても普通の用途は動く」ことであり、
表現できないものを無理に CIM で書いて黙殺されるくらいなら PS に落とす方が正しい。

### 扱えない入力への対処は 2 通りある

CIM 経路で扱えない入力に当たったとき、**自動で PS に落とす**か **エラーで止める**かを
ケースごとに選び分けている。基準は次のとおり。

| 対処 | 選ぶ条件 |
|---|---|
| 自動で PS に落とす | 利用者が意識せずとも正しい結果になる場合(read の一部、ゼロ値ダウングレード等) |
| エラーで止める | 落としても正しく動く保証がない、または将来の実装で挙動が変わる場合(高度なオプション群) |

**どちらの場合も「黙って成功を返す」ことはしない。** これが唯一の禁止事項。

> **どの条件がどちらになるかの現況は [README](../../README.md) を参照。**
> ADR は追記のみのファイルなので、ここに現況の一覧を置くと確実に陳腐化する。

**「達成した」と丸めない。** `CLAUDE.md` にも
「未達がある場合は残る部分を正確にスコープ明記する」と定めてある。
2026-08-27 時点で PS 0 件のフルライフサイクルが成立するのは使い捨ての検証用 VM のみで、
実運用の構成では PS が動く。

### 見直しの条件

- [ ] CIM 経路が全リソースを覆った → PS 実装の削除を検討する(それまでは消さない)
- [ ] 既定を CIM 経路にできる程度に穴が塞がった → `HYPERV_USE_WSMAN` の既定値を反転する
- [ ] 埋め込み方式が原因で追いにくいバグが出た → 明示的なインターフェース分割を再検討する
